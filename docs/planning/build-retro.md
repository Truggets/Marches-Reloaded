# Build Retro

Running log of what happened at the end of each `trugg-build` milestone — kept short, appended per milestone.

## M7 — 8-bit avatars (2026-07-19)

**What shipped:** deterministic client-side pixel-art avatars (DiceBear, CC0), shown on the character list and sheet, seeded by each character's stable id — no schema/server change.

**What broke or surprised us:** the M7 *deploy* (not the feature itself) caused a real, if brief, production outage. `scripts/deploy.sh`'s release-pruning step and `scripts/rollback.sh`'s default-target selection both sorted release directories by mtime (`ls -t`) to find newest/oldest — but every release is populated via `rsync -a` from the same persistent `$REPO_DIR` working copy, which preserves that source's mtimes, so release directories can end up with identical/stale mtimes. The prune step mistook the release it had *just deployed* for the oldest one and deleted it; the `current` symlink was left pointing at nothing and the whole site 404'd (not just the avatar feature). A first rollback attempt (`rollback.sh` with no argument) picked the *wrong* release for the exact same reason, before an explicit-by-name rollback recovered the site.

**What that changes going forward:** fixed both scripts to sort release directory names (timestamp-prefixed, so lexicographic order == chronological order) instead of relying on mtime — commit `014e566`. Added to `trugg-build`'s own process (this file, plus a §9 "Retro" step) so future milestones' deploys get checked against known deploy-script gotchas rather than re-discovering them. General lesson: **don't trust `ls -t`/mtime-based sorting for anything populated via `rsync -a` from a shared, reused source directory** — mtimes there reflect the source's history, not "when this copy was made."

**Follow-up (same day):** pushing the fix to git wasn't enough on its own — the running `deploy.sh`/`rollback.sh` on the VPS are standalone copies at `/opt/marches-reload/scripts/` that the release pipeline never overwrites (nothing syncs `scripts/` out of a release into that path). Had to patch the live files directly via the VPS terminal, verify `bash -n` and dry-run the prune logic read-only against the real release directory, then retry the M7 deploy as a canary before trusting the fix. **New rule for this class of bug going forward: a script fix living only in git does not fix production — check whether the runtime path actually re-reads from the repo, and if not, patch the deployed copy directly and verify it in place before the next real deploy.**

## Post-M7 QA bug-fix pass (2026-07-19)

**What shipped:** an independent human QA pass (12 SRD classes created and leveled 1→5 through the real UI, not just engine tests) surfaced 5 findings. Two fixed this session: a Bard/Druid prepared-spell over-grant in the level-up stepper (M5), and two never-implemented Human bonus-choice traits, Skillful and Versatile (M3).

**What broke or surprised us:** both real bugs were UI-layer, not engine-layer — the rules-engine unit tests (37+ of them by this point) never had a chance to catch either, because they were never wired up to read data (`preparedOrKnown`, the species trait list) that had been sitting correctly in the bundled pack the whole time. A thorough engine test suite gives false confidence about UI wiring it never exercises. Also notable: 2 of the 5 QA findings weren't new bugs at all — they were scope cuts already explicitly documented in earlier milestone rows (Unarmored Defense, non-interactive subclass choice). Worth re-confirming "is this already a known, accepted gap?" against the spec before treating a QA finding as new work.

**What that changes going forward:** when a milestone's "done" definition includes a UI flow that derives a number or offers a choice from data, add at least one test that exercises the derivation through real bundled data (not just that the underlying data field exists) — the Bard/Druid bug is exactly the gap between "the data has the right value" and "the code reads it." For species/class traits described as prose in the data but meant to grant a mechanical choice (any trait whose description says "of your choice"), check at build time whether a wizard step actually exists for it — this is the second time in this project a flavor-text trait had no code behind it.

## M8 — Polish & party view (2026-07-19)

**What shipped:** admin-only party view (`GET /api/admin/characters` + `PartyViewPage.tsx`), inline character rename, an app-wide `ErrorBoundary`, a catch-all 404 route, and one real responsive fix. Scope was narrowed up front with Truman (rename-only "edit," dice roller skipped) rather than guessed.

**What broke or surprised us:** nothing broke, but verifying two DoD items honestly (party view's admin-vs-non-admin authorization, and the error boundary actually catching a render error) required a logged-in admin session and a component that actually throws — neither of which existed to click through. Building throwaway test accounts directly in the local dev DB (via a one-off script using the server's own db module, argon2-hashed, deleted immediately after each check) turned out to be the right call rather than skipping the negative-case checks or guessing they'd work. Also: the server process for local dev wasn't running via `--watch`, so a new route (`/api/admin/characters`) silently 404'd until the process was restarted — worth checking `ps`/`package.json`'s dev script before assuming a running dev server will pick up new server-side routes.

**What that changes going forward:** for any milestone whose DoD includes "X is blocked for non-Y" or "an error shows a fallback," the verification has to actually construct the blocked/failing case — a cosmetic check (nav link hidden, code compiles) is not the same claim as the DoD makes. Throwaway local-dev test accounts (created directly via the app's own db connection, never touching `.env`/secrets, deleted right after) are a reasonable, low-risk way to get into a state (admin session, specific user) that the current logged-in session can't reach. Also: confirm whether the local dev server process actually watches for changes before trusting "restart isn't needed" — plain `node src/index.js` (no `--watch`) is silently stale.

## Post-M8 bug-fix pass (2026-07-21)

**What shipped:** Truman reported 16 real-play issues; investigated each against the actual code (not memory) before deciding anything, then fixed 5 isolated bugs plus one self-contained feature (a persistent "Class Features" section on the sheet, which turned out to explain 3 of the 16 complaints at once). The other ~8 items are real but bigger — logged as open follow-up work, not silently dropped or rushed.

**What broke or surprised us:** nothing broke, but two things stood out during investigation. First, several "new bugs" Truman found were actually already-documented accepted scope cuts resurfacing (Unarmored Defense, no spell re-preparation, no proficiency/attack-bonus modeling) — the second time this session that re-confirming against PROJECT_SPEC's existing known-gaps list before treating something as new work paid off. Second, deleting a throwaway test user via a script while it still owned a character hit a foreign-key constraint (`characters.owner_id` and a stale `sessions` row both referenced it) — cleanup order matters: character rows, then session rows, then the user row, not just the user row.

**What that changes going forward:** when a user reports a batch of issues, don't triage from memory or gut feel — grep/read the actual code for each one first (a forked/delegated investigation pass works well for this at volume) before proposing what's a quick fix vs. a real feature vs. an already-accepted gap. When cleaning up throwaway local-dev test data that includes both a user and dependent rows (characters, sessions), delete child rows before the parent, or the DB's own foreign-key constraints will (correctly) refuse the delete.

## GitHub issue reconciliation + Wilbur building-advice feature (2026-07-21)

**What shipped:** discovered a playtester had independently filed 11 GitHub issues covering almost the same bug list Truman reported in chat — closed the 4 fully-fixed ones with fix-reference comments, partially-closed one (#11) with a comment splitting out the still-open Unarmored Defense AC-math gap into a new issue, and opened 2 new issues for gaps that had no existing issue (Unarmored Defense AC math, feat-data curation). Separately, built a new `WilburTip` component giving contextual building advice (primary ability, species traits, background feat) on every step of character creation.

**What broke or surprised us:** browser-automation click-registration was flaky throughout this session's manual verification — a `find`+click on a button would sometimes show the button as visually "selected" (a stray hover/focus style) without the underlying React state actually updating, which looked exactly like a real bug in the new feature (the tip text wasn't updating) until cross-checked against a second signal (the step-count total, which depends on the same state) that proved the click truly hadn't registered. A coordinate-based click immediately after a screenshot was reliable every time; `find`-returned refs were not.

**What that changes going forward:** when a manually-driven verification shows a suspicious result (a tip not updating, a state not changing), check a second independent signal before concluding the code is broken — here, the step-count total corroborated that the class selection itself hadn't taken effect, which pointed at a click-reliability problem instead of a feature bug. Don't trust a single visual cue (a button "looking" selected) as proof of state; verify via a value that's provably derived from that state.

## M2b Phases 1-4 — admin content-pack import (2026-09-08/09)

**What shipped:** the full v1 scope of M2b (feats, backgrounds, species, equipment), built as 4 separate phases over two sessions, each following the same shape: a parallel-worker parse-pack-review-commit loop mirrored from Phase 1 onward. `POST /api/admin/packs/import` now handles all 4 content types as independently-optional fields with per-type merge-on-conflict (importing one type never wipes another already stored under the same pack id), `AdminPackImportPage.tsx` has one textarea per type, and `ContentPicker.tsx` (generalized from a feats-only `FeatPicker`) renders species/background/feat pickers alike. `EquipmentEntry` gained structured `damage`/`mastery`/`ac`/`strength`/`stealth` fields, applied to both the bundled SRD parser and the new import parser, so real weapon-attack math (M11) has real data to read once built.

**What broke or surprised us:** the review-as-it-lands practice (adopted mid-Phase-2 per an org-design update, replacing "batch all commits until every reviewer reports") caught real bugs every single phase it ran on, not just once — Phase 2's parser leaked raw markdown into a plain-text UI field and had an unvalidated skill-name extraction; Phase 3's species parser had a case-sensitive rename/lookup that would silently mis-name a differently-cased vault trait rather than throwing (the exact "silently wrong, not empty" failure class this whole codebase's import parsers are built to avoid); Phase 4's equipment `clean()` helper only recognized one of several real "no value" placeholder spellings. None of these were hypothetical — each was demonstrated against real data or a real fixture. A design decision surfaced mid-Phase-3/4 that wasn't anticipated by the original M2b execution plan: whether `EquipmentEntry` needed real structured mechanical fields or could stay prose-only like the bundled pack always had — resolved by asking directly rather than assuming, since it changed the shape of already-shipped bundled data (`data/equipment.json`) and had a real tradeoff (schema churn now vs. `M11` staying blocked regardless of Phase 4 landing).

**What that changes going forward:** per-piece review (not batched) is now confirmed valuable across 3 consecutive phases, not a one-off — keep it as the default for parallel-worker builds in this repo. When a parser or validator's whole design principle is "throw rather than silently produce a wrong-but-non-empty value," explicitly test the case-sensitivity/normalization of every string-based lookup or rename map it uses — a reviewer's hand-traced logic check caught this every time real execution wasn't available to the reviewing agent, so don't skip that style of review just because a tool (Bash) is unavailable to the reviewer. When a phase's design has a real schema/scope fork that affects already-shipped data, surface it as an explicit decision point rather than picking a default and mentioning it after the fact — the equipment structured-fields question resolved in one `AskUserQuestion` round-trip and avoided building the wrong shape twice.

## M11 — Combat sandbox caster-only v0 (2026-09-09)

**What shipped:** the full caster-only v0 from `docs/planning/m11-sandbox-v0-plan.md` — a new `MonsterEntry` schema category with 10 curated low-CR monsters sourced from the same already-pinned upstream commit every other bundled category uses, `resolveSpellAttack`/`resolveMonsterAttack` turn-resolution functions with a curated 9-cantrip damage lookup (deliberately not a full 339-spell parse — a hand-curated lookup covering the actual SRD attack-roll cantrip list, matching an existing precedent in this repo), and a `/characters/:id/sandbox` page. Built in 3 rounds (data+parser, engine+lookup, UI), each reviewed as it landed, same shape as M2b's phases.

**What broke or surprised us:** the review pattern's track record extended to a 4th consecutive build in a row — a real bug caught every round, not diminishing returns. Round 1's monster parser had an attack-roll detection regex narrower than the real SRD phrasing it needed to catch (matched today's 10 monsters, would've silently dropped damage data on a future one using different real wording). Round 3's UI had two genuine multiclass-correctness bugs: HP/AC computation validated only `classes[0]`'s class id before calling functions that iterate every class and throw on an invalid one, and caster-class selection took the first spellcasting-shaped class it found rather than considering all of them — silently wrong (not just missing) for a real Cleric/Wizard dual-caster build, since it would show the wrong ability score's attack bonus for whichever cantrips happened to display. Both were things a "does it build, do the existing tests pass" check would never have caught, since they only manifest for specific class combinations nobody had a test for. Also notable: the original UI research proposed a CSS-grid battle-token view; implementation correctly recognized that once the turn-resolution logic was the actual hard part (already built and tested), a flat two-panel picker/log layout delivered the same v0 functionality for much less UI surface — a good example of implementation catching a plan's scope creep rather than building what was originally sketched just because it was written down.

**What that changes going forward:** silent multiclass-correctness bugs keep showing up specifically in code that "iterates every class" vs. code that only checks `classes[0]` — this is now the 2nd+ time in this project's history (see the M5/M6 rows in PROJECT_SPEC.md) that a first-class-only assumption caused a real bug for genuine multiclass builds. When reviewing any new code that touches `CharacterData.classes`, explicitly check whether it handles N classes or silently assumes 1, especially for anything selecting "the" caster/primary class — CLAUDE.md already calls out "don't silently optimize away multiclassing correctness" as a standing rule; this session is concrete evidence why. A plan doc's proposed UI shape is a starting point, not a contract — if implementation reveals the actual hard part is elsewhere and a simpler UI ships the same v0 value, take it and say so explicitly in the plan doc's close-out, rather than either over-building to match the original sketch or silently deviating without a note.

## M11 Phase 2 — martial weapon attacks in the combat sandbox (2026-09-09)

**What shipped:** `docs/planning/m11-phase2-weapon-attack-plan.md`'s full scope — `parseWeaponsFromEquipmentChoice()` resolves a character's starting-equipment letter into concrete weapon entries (`client/src/engine/equipmentAttack.ts`), `resolveWeaponAttack()` mirrors the existing spell/monster resolvers, and both wire into `CombatSandboxPage.tsx` as a weapon picker alongside the existing cantrip picker. No `data/schema.ts` change was needed — the orientation pass verified (against all 38 bundled weapons, zero exceptions) that ability-for-attack derives cleanly from each weapon's existing `properties` string (Finesse → higher of STR/DEX, Ammunition-without-Finesse → DEX, else STR), which the caster-only v0's retro entry above didn't have an equivalent for. Explicitly scoped separately from issue #3's literal text (a Fighting Style/Weapon Mastery *selection UI* for the wizard) — that stays untouched and open; only the sandbox-combat half shipped here.

**What broke or surprised us:** review (an opus reviewer against a sonnet builder, per this session's new model-assignment policy) caught two real things before push, one in each of the two already-reviewed engine pieces' consuming code: (1) the weapon-picker's prose parser initially dropped a real weapon named inside a focus parenthetical — "Arcane Focus (Quarterstaff)" (Wizard) and "Druidic Focus (Quarterstaff)" (Druid) both silently lost their actual melee weapon, since the whole-token match never split out the parenthetical; a Wizard picking option A would've had only a Dagger, missing a strictly better weapon they actually owned. (2) The UI wiring passed `weapon.damage` straight through with no ability modifier — SRD 5.2 weapon attacks add the same ability modifier used for the attack roll to the damage roll (unlike cantrip damage, which doesn't scale with casting ability), so a hit's tracked HP loss was silently low. Both were caught by a reviewer that had NO shell access this run (Bash was disabled in its sandbox) and said so explicitly rather than fabricating a "tests pass" claim — it hand-traced the parser against real `data/classes.json`/`data/equipment.json` content and reasoned about the resolver's type contracts instead, then flagged that the parent session needed to actually run the commands. The parent then verified both independently before applying fixes.

**What that changes going forward:** a reviewer without a shell is still valuable if it says so plainly and reasons from source instead of guessing — the discipline of "verification caveat, read first" at the top of a review report should be treated as reliable signal, not a weakness to route around; the fix is for the orchestrating session to always independently run the real commands before trusting any review's pass/fail claim, regardless of what the reviewer says it did. Also: cross-referencing two related but structurally different pieces of prose (player weapon damage vs. curated cantrip damage vs. monster action damage) is exactly where an asymmetric rule (ability mod applies to one, not the others) is easy to miss when building the new piece by analogy to the two existing ones — when mirroring an existing pattern for a new but rules-distinct case, explicitly re-derive the actual game rule rather than assuming "shaped like the others" implies "behaves like the others."
