# Build Retro

Running log of what happened at the end of each `trugg-build` milestone — kept short, appended per milestone.

## M7 — 8-bit avatars (2026-07-19)

**What shipped:** deterministic client-side pixel-art avatars (DiceBear, CC0), shown on the character list and sheet, seeded by each character's stable id — no schema/server change.

**What broke or surprised us:** the M7 *deploy* (not the feature itself) caused a real, if brief, production outage. `scripts/deploy.sh`'s release-pruning step and `scripts/rollback.sh`'s default-target selection both sorted release directories by mtime (`ls -t`) to find newest/oldest — but every release is populated via `rsync -a` from the same persistent `$REPO_DIR` working copy, which preserves that source's mtimes, so release directories can end up with identical/stale mtimes. The prune step mistook the release it had *just deployed* for the oldest one and deleted it; the `current` symlink was left pointing at nothing and the whole site 404'd (not just the avatar feature). A first rollback attempt (`rollback.sh` with no argument) picked the *wrong* release for the exact same reason, before an explicit-by-name rollback recovered the site.

**What that changes going forward:** fixed both scripts to sort release directory names (timestamp-prefixed, so lexicographic order == chronological order) instead of relying on mtime — commit `014e566`. Added to `trugg-build`'s own process (this file, plus a §9 "Retro" step) so future milestones' deploys get checked against known deploy-script gotchas rather than re-discovering them. General lesson: **don't trust `ls -t`/mtime-based sorting for anything populated via `rsync -a` from a shared, reused source directory** — mtimes there reflect the source's history, not "when this copy was made."

**Follow-up (same day):** pushing the fix to git wasn't enough on its own — the running `deploy.sh`/`rollback.sh` on the VPS are standalone copies at `/opt/marches-reload/scripts/` that the release pipeline never overwrites (nothing syncs `scripts/` out of a release into that path). Had to patch the live files directly via the VPS terminal, verify `bash -n` and dry-run the prune logic read-only against the real release directory, then retry the M7 deploy as a canary before trusting the fix. **New rule for this class of bug going forward: a script fix living only in git does not fix production — check whether the runtime path actually re-reads from the repo, and if not, patch the deployed copy directly and verify it in place before the next real deploy.**

## Post-M7 QA bug-fix pass (2026-07-19)

**What shipped:** an independent human QA pass (12 SRD classes created and leveled 1→5 through the real UI, not just engine tests) surfaced 5 findings. Two fixed this session: a Bard/Druid prepared-spell over-grant in the level-up stepper (M5), and two never-implemented Human bonus-choice traits, Skillful and Versatile (M3).

**What broke or surprised us:** both real bugs were UI-layer, not engine-layer — the rules-engine unit tests (37+ of them by this point) never had a chance to catch either, because they were never wired up to read data (`preparedOrKnown`, the species trait list) that had been sitting correctly in the bundled pack the whole time. A thorough engine test suite gives false confidence about UI wiring it never exercises. Also notable: 2 of the 5 QA findings weren't new bugs at all — they were scope cuts already explicitly documented in earlier milestone rows (Unarmored Defense, non-interactive subclass choice). Worth re-confirming "is this already a known, accepted gap?" against the spec before treating a QA finding as new work.

**What that changes going forward:** when a milestone's "done" definition includes a UI flow that derives a number or offers a choice from data, add at least one test that exercises the derivation through real bundled data (not just that the underlying data field exists) — the Bard/Druid bug is exactly the gap between "the data has the right value" and "the code reads it." For species/class traits described as prose in the data but meant to grant a mechanical choice (any trait whose description says "of your choice"), check at build time whether a wizard step actually exists for it — this is the second time in this project a flavor-text trait had no code behind it.
